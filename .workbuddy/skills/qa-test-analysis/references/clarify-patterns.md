# 澄清提问模式（clarify-patterns）

对待澄清项，用**具体、可答、带上下文**的问题发起澄清，避免「这个需求清楚吗」式无效提问。

## 提问公式
> 在 <模块/场景> 下，当 <前提> 时，<不确定点> 应该 <期望的哪种行为>？例如：<选项A> 还是 <选项B>？

## 常见提问模板
1. **边界类**：昵称最长允许多少字符？超过时提示什么？
2. **异常类**：提交失败（网络/服务异常）时，数据是否回滚？用户看到什么？
3. **权限类**：游客 / 普通用户 / 管理员，对这个按钮分别可见可操作吗？
4. **状态类**：订单取消后，已支付金额如何处理（退款/冻结）？
5. **数据类**：删除部门时，其下员工如何处置（禁止删除/转移/级联）？
6. **依赖类**：这个功能依赖的 XX 服务，测试环境是否已就绪？

## 交互纪律
- 一次列出 3–6 个最关键的澄清项，分批推进，不要一次性抛出 20 个。
- 每项给出推荐默认值（附理由），让用户「确认 / 修正」即可，降低决策成本。
- 澄清结果即时回填需求文档第 7 节与 `clarifications.md`。
- 澄清未完成前，涉及该项的测试点标注「依赖澄清」，暂不生成用例。
