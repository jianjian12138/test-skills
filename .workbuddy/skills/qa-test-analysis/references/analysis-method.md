# 需求分析方法（analysis-method）

将结构化需求拆解为「可测项 / 风险点 / 依赖 / 待澄清项」的实操方法。

## 1. 可测项提炼
把每个功能点改写为可验证陈述，模板：
> 当 <前置条件>，用户执行 <操作>，系统应 <可观测结果>。

例：
- 功能点：「用户可修改昵称」
- 可测项：「已登录用户进入个人资料页，修改昵称为 1–20 位合法字符并提交，系统提示保存成功且列表展示新昵称」

## 2. 风险点识别（标注高/中/低）
从以下维度找高风险区：
- **历史漏测区**：过往缺陷集中的模块。
- **逻辑复杂**：状态机、金额计算、权限矩阵、并发。
- **外部依赖**：第三方接口、消息队列、定时任务。
- **数据敏感**：支付、隐私、权限。
- **易变**：需求中明确「待定」「后续」的部分。

## 3. 依赖与前置
列出执行测试前必须满足的条件：
- 环境：测试地址、可用账号（不同角色）、基础数据。
- 数据：需预置的订单/配置/字典。
- 工具：接口文档、数据库可读权限。

## 4. 待澄清项
凡出现以下情况，列为待澄清：
- 需求矛盾（A 必填 vs B 可选）。
- 模糊表述（「优化」「支持」「合理」）。
- 缺异常定义（失败怎么办、超时怎么办）。
- 缺边界（最长多少、最大上传多大）。
- 缺权限说明（谁能看/改）。

> 待澄清项必须带「影响说明」：会阻塞哪些可测项 / 测试点的设计。
