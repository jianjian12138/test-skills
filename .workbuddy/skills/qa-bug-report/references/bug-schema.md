# 缺陷字段 Schema（qa-bug-report）

```json
{
  "title": "下单页提交后无响应",
  "module": "下单",
  "type": "ui|api|perf|security",
  "severity": "S1|S2|S3|S4",
  "priority": "P0|P1|P2|P3",
  "env": "dev|test|staging|prod",
  "reporter": "测试人",
  "assignee": "开发人",
  "version": "可选，发现版本",
  "steps": ["步骤1", "步骤2", "步骤3"],
  "expected": "期望结果",
  "actual": "实际结果",
  "evidence": "截图/日志/录屏路径，可多个",
  "impact": "可选，业务影响"
}
```

## 严重级（Severity）定义

| 级别 | 含义 | 示例 |
| --- | --- | --- |
| S1 致命 | 核心功能不可用 / 数据丢失 / 安全泄露 | 下单报错丢单、越权改他人数据 |
| S2 严重 | 主要功能异常，无替代方案 | 支付失败但已扣款 |
| S3 一般 | 次要功能异常，有替代 | 列表排序错、文案错 |
| S4 轻微 | UI 瑕疵 / 易用性 | 错位、颜色 |

## 优先级（Priority）与严重级的关系

- 严重级描述「问题有多坏」，优先级描述「多快修」。
- 通常 S1→P0、S2→P1；但 S4 若涉及核心流程入口也可升 P0（如首页白屏）。

## 证据清单

- 截图 / 录屏（必有）
- 请求/响应（接口类必有）
- 日志片段（后端类）
- 复现概率（必填：必现 / 偶现 / 难以复现）
