# AI 假通过模式清单（AI False-Pass Patterns）

> 来源（行业对标）：简礼/AliExpress《Agent 自规划执行实践 UI 测新》的「AI 假通过 v2 严口径 9 条 + BLOCKED 快速路径」；
> 木槿年《TestCase-UIAuto》的「永真断言黑名单 + 步骤对照表」。
> 本清单为**判分/断言治理的通用红线**，适用于 `qa-execution` / `qa-ui-automation` / `qa-agent-eval(grade_run)` / `qa-test-case-gen`。

核心理念：**AI 说自己成功 ≠ 真的成功**。"跑全量看通过率"会掩盖假绿，必须以**可执行断言 + 永真断言黑名单 + BLOCKED 快速路径**替代。

## 一、9 条 AI 假通过模式（命中即判 blocked / invalid）

| # | 模式 | 说明 | 正确做法 |
|---|---|---|---|
| 1 | **前置态未构造** | 直接断言目标态，没先确保初始条件满足（如未登录就断言"下单成功"） | 先构造/校验前置态，再断言目标态 |
| 2 | **单帧终态推时序** | 用一张终态截图/状态推断整个时序正确 | 关键步骤逐帧/逐事件断言，禁止单帧推全程 |
| 3 | **"没看到就是通过"** | 元素/字段不存在就判 pass（未验证"该不该存在"） | 元素缺失 = 失败，除非显式声明"可缺省" |
| 4 | **环境异常页当降级** | 把 500/错误页当成"功能正常降级"通过 | 错误页 = 阻断，降级须显式约定且可观测 |
| 5 | **UI 判后端 payload** | 用 UI 展示推断后端返回，而非查真实接口 | 断言查真实接口/数据库，不靠 UI 文本推测 |
| 6 | **Agent 未完成关键动作就 finish** | 任务没真做完（缺关键工具调用/状态写入）就报完成 | finish 前校验关键动作轨迹已落地 |
| 7 | **平台不支持当通过** | 把"平台能力不支持"当作测试通过 | 不支持须标记 skip/blocked，不得记 pass |
| 8 | **断言意图错位** | 断言了不相关的东西（如只断言页面标题含品牌名） | 断言必须对准被测意图的语义结果 |
| 9 | **配置对照缺失** | 没对照期望配置/基线就判"一致" | 断言须对照期望配置（diff），不得裸比 |

## 二、永真断言黑名单（W2/W10）

> 把下面这些词作为**唯一**断言时，断言永远为真 → 无效，必须改。

- 通用肯定词：`ok` / `success` / `done` / `completed` / `passed` / `响应` / `成功` / `完成` / `通过` / `页面` / `加载` / `存在` / `loaded` / `page`
- **自检方法**：「如果把操作步骤全部注释掉，断言还能通过吗？」——能通过 = 无效（永真），必须补充语义断言（status/body/error/具体业务字段/工具序列）。
- `grade_run.py` 内置 `is_trivial_checker()`：当 checkers 仅有上述通用词（且无 tool_sequence）时，标记 `trivial_assertion`；`--block-trivial`（默认开，fail-closed）将判 `trivial_assertion_blocked`（exit 2）。

## 三、BLOCKED 快速路径（W9）

命中上述任一模式时，**立即判 `blocked` / `invalid` 并 finish**，不硬滑（反复重试/烧 token）去"凑"一个 pass。BLOCKED 是合法结论，不是失败——它保护 CI 不被假绿污染，也避免无意义算力消耗。

## 四、配套纪律

- **通过率下降 ≠ 坏事**：挤掉虚高后通过率可降，须追"通过率与有效率一致性"（见 W9 能力探针基线）。
- **步骤对照表**：生成用例后强制"用例步骤 ↔ 代码实现"逐条对照，防"11 步只实现 3 步"。
- **调试三轮制**：3–5 关键 → 仅失败 → 全量；超 3 轮标记待人工。
