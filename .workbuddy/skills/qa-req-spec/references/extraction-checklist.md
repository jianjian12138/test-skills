# 需求抽取检查单

从原始材料（PRD / 用户故事 / 原型标注 / 截图描述 / 会议记录）中抽取信息时，逐条核对。
缺失即记入「待澄清项」，不要编造。

## A. 业务层
- [ ] 背景与目标是否清晰？是否可度量？
- [ ] 本次变更范围边界是否明确（哪些做、哪些不做）？

## B. 功能层（每个模块）
- [ ] 入口在哪里？（菜单 / 按钮 / 链接 / 路由）
- [ ] 主操作流程是什么？（分步列出）
- [ ] 有哪些字段？类型 / 必填 / 格式 / 枚举是否齐全？
- [ ] 操作成功后的预期表现？
- [ ] 操作失败 / 异常时的提示文案与触发条件？

## C. 数据与状态
- [ ] 数据是否需要唯一性校验？（用户名、订单号等）
- [ ] 状态机 / 流转规则是否完整？（草稿→提交→审核→完成）
- [ ] 关联数据如何处理？（级联、外键、删除时的子项）

## D. 权限与角色
- [ ] 哪些角色能看 / 能改 / 不能看？
- [ ] 越权访问的预期行为？（提示无权限 / 隐藏入口）

## E. 非功能
- [ ] 是否提及性能目标（RT / TPS / 并发）？
- [ ] 是否提及安全要求（鉴权、加密、脱敏、审计）？
- [ ] 是否提及兼容性（浏览器 / 端 / 分辨率）？

## F. 矛盾与模糊
- [ ] 材料之间是否存在冲突？（A 说必填，B 说可选）
- [ ] 是否有「支持」「优化」「友好」等不可测的模糊表述？
- [ ] 是否有依赖外部系统 / 第三方？（需环境就绪）

> 任何勾选为「否 / 缺失 / 模糊」且影响测试设计的，必须写入需求文档第 7 节「待澄清项」。
