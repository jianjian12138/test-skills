# 核心测试工程宪章：场景是骨、接口是肉、双轴为尺 (v12.1.0)

## 1. 为什么需要明确“以业务场景为基础”的边界？

在测试工程与 AI 辅助测试中，对“以业务场景为基础”必须按**设计、验收、度量**三个层级严格区分：

| 准则维度 | 工程判定 | 核心理由与反模式警示 |
| :--- | :--- | :--- |
| **测试设计准则**：先有场景，再有用例 | **成立，且是最优先铁律** | 用例是从业务场景切出来的；若脱离场景直接对着孤立接口切用例，极易产出一堆业务上绝不会发生的无效断言，同时漏掉跨节点状态断裂。 |
| **上线验收准则**：场景全绿才允许上线 | **成立，但仅是必要条件** | 场景全绿只保证“正常用户顺着主干道能走通”（Happy Path），并不保证每个节点的边界极值、并发性能、跨租户权限与安全注入没问题。 |
| **质量度量准则**：用场景通过率代替覆盖率 | **不成立（严禁替代）** | 一条业务场景只覆盖一条代码执行路径；10 条核心场景 100% 全绿，不代表 46 个通用技能所对应的边界、异常码、BOLA 越权和死锁分支都被测过。 |

> **总纲结论**：**场景是骨，接口/节点是肉，双轴是尺**——业务场景决定测什么、按什么顺序测、什么算业务走通；单接口/单节点通用技能负责把每个节点的边界值、异常码、权限、性能打穿；最终由“场景连通率（必要条件）× 节点深潜覆盖率（充分条件）”双轴门禁共同裁决。

## 2. 三层正交解耦架构（宪章 — 模具 — 通用刀片）

1. **顶层宪章（Testing Charter）**：以“骨、肉、尺”统领测试设计、执行与放行门禁（由 `qa-orchestrator` 执行编排）。
2. **中间层：可插拔业务场景模板（Scenario Templates）**：位于 `skills/templates/`，提供与具体行业解耦的标准化场景骨架填空模具，定义状态流转、逆向补偿、守恒律与节点技能挂载槽。
3. **底层：46 项通用原子 QA 技能（Universal Atomic Skills）**：位于 `skills/qa-*/`，保持 100% 纯技术通用性，不耦合任何特定行业业务逻辑，随插随用。
