# qa-incident-retro (生产事故时间线复盘与改进项闭环跟踪) — 领域深度参考指南

## 1. 核心检查清单 (Core Verification Checklist)
- **时间线四时刻模型**：必须还原 `T0 告警触发` → `T1 人工发现/确认` → `T2 止血完成` → `T3 服务完全恢复`；每个时刻需附证据来源（监控截图链接、trace_id、告警 ID），无证据的时间戳标注「待确认」而非编造。
- **根因双层追问**：先写直接原因（如「连接池耗尽」），再用 5 Why 追到系统性根因（如「容量评估未覆盖宣传峰值 → 压测场景缺失 → 上线门禁无容量红线」）。只写直接原因视为复盘不合格。
- **改进项 SMART 验收**：每条改进项必须同时具备责任人（真实姓名或角色 owner）、截止日期（YYYY-MM-DD）、验收标准（可判定的条件，如「压测报告覆盖 3 倍峰值且 P99 < 500ms」）。三者缺一，报告状态为 `BLOCKED`。
- **无责复盘原则 (Blameless)**：描述行为与系统缺陷，不指责个人；聚焦「系统为何允许该错误发生」而非「谁犯了错」。
- **隐私与密钥防线**：时间线与日志摘录中的用户 ID、手机号、身份证、IP、密钥必须先经 `sanitize_sensitive_data` 脱敏；内部生产 IP 不得出现在对外交付的复盘文档中。

## 3. 关联工具与阶段协同
- **生命周期阶段**：`release_ops`
- **推荐协同技能**：`qa-log-triage`（按 trace_id 还原跨服务链路）、`qa-release-check`（把改进项转为上线红线门禁）、`qa-archive`（把复盘产物版本化归档）。
- ** CLI 探测**：`python3 qaskills.py route "生产事故时间线复盘与改进项闭环跟踪"`。
