# qa-prompt-refine (模糊测试指令打磨) — 领域深度参考指南

## 1. Skill 三条门槛（判断「什么才算 Skill」）
1. **有明确触发条件**：写清「什么情况下用它」，让模型可判断，而不是每次靠人想起来。反例：「帮我测一下」；正例：「当用户提供 PRD 或需求描述时，按模块拆出可测点」。
2. **有固定输出格式**：同样的问题问三次，产出结构必须一致，否则使用者还要重新整理。推荐三列表格（模块 / 功能 / 风险）或结构化 JSON。
3. **有可验收边界**：完成后能一眼看出对不对、缺不缺。例：「风险列不少于 3 条，不确定的条目标注意外」。

最容易被忽略的是第三条——没有验收标准的 Skill，用起来爽、收尾全靠人补，只是把活推后了。

## 2. 模糊词黑名单（命中即判定未通过）
`尽量`、`适当`、`差不多`、`大致`、`视情况`、`合理`、`尽快`、`可能的话`、`等等`、`相关`。
改写时必须替换为可判定的量化条件（数量、时间、格式、阈值）或明确标注「需澄清」。

## 3. 反例 → 正例对照
- 反例：「帮我写一下这个需求的用例」
- 正例：「当用户提供 PRD 或需求描述时，按模块拆出可测点，输出三列表格（模块/功能/风险），风险列不少于 3 条，不确定的条目标注意外。」
差别不在长度，而在于把「什么时候用、输出长什么样、什么算做完」三件事写死。第一次多花 20 分钟，之后每次都不用再想。

## 5. 关联工具与阶段协同
- **生命周期阶段**：`requirements`
- **推荐协同技能**：`qa-req-spec`（把模糊需求结构化）、`qa-test-analysis`（把改写后的指令落到可测点）。
- **CLI 探测**：`python3 qaskills.py route "提示词打磨"`。
