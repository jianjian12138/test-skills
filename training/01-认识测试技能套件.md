# 第 1 篇：认识这套测试技能套件（全景地图）

> 本篇目标：用最短的篇幅让你明白「这到底是什么、能帮你做什么、由哪些部分组成」，建立起整体心智模型。读完你就能看懂后面 9 篇在讲什么。

---

## 1.1 一句话介绍

这是一套 **WorkBuddy 全栈测试技能套件（QA Skills）**：它把软件测试从「需求」到「归档」全流程里常用的 40 个测试能力，打包成一个个**可以独立调用、即插即用**的技能（Skill）。

你不需要记住 40 个工具的命令。你只要**用大白话告诉 AI「我要测什么」**，它就会加载对应的技能帮你把活干完——产出规范文档、用例表格、接口脚本、测试报告等。

> 它解决的核心痛点：**需求、用例、接口、执行、报告散落在多个工具、难以追溯**。本套件让一轮测试的每件产物都有固定归属、可复用、可复盘。

---

## 1.2 它长什么样？——40 个技能的组成

套件共 **40 个技能**，分两大家族：

| 家族 | 数量 | 说明 | 是否接入生命周期路由 |
|---|---|---|---|
| **传统 QA 技能** | 38 个 | 覆盖完整测试生命周期 + 横切质量门禁（**含 `qa-orchestrator` 编排入口**） | 是（编排器会路由） |
| **Agent 测试专属技能** | 2 个 | 评测「AI Agent 本身」的能力与安全性 | 否（独立专题，见第 10 篇） |

> 注意：38 个传统技能里已**包含 `qa-orchestrator` 编排入口与 11 个横切质量门禁**，不是额外叠加。所以 38 = 1 个编排入口 + 27 个阶段技能 + 11 个横切门禁。另有 2 个 Agent 测试专属技能（不接入 8 阶段路由）。

---

## 1.3 八阶段生命周期（主骨架）

传统 QA 技能围绕一条 **8 阶段生命周期** 组织。理解这条线，你就理解了 90% 的内容：

```
需求(01) → 分析(02) → 用例(03) → 数据/环境(04) → 接口文档(05)
   → 执行(06) → 报告/缺陷/发布(07) → 归档(08)
```

每一阶段对应一个或多个技能，举几个典型：

| 阶段 | 目录 | 代表技能 | 它帮你做 |
|---|---|---|---|
| 01 需求 | `01-requirement` | `qa-req-spec` | 把零散需求整理成规范文档 |
| 02 分析 | `02-analysis` | `qa-test-analysis` | 拆解可测点、主动澄清模糊项 |
| 03 用例 | `03-cases` | `qa-test-case-gen` | 一键生成 Excel/Xmind 用例 |
| 04 数据环境 | `04-testdata` | `qa-test-data` / `qa-env-config` | 造数据、脱敏、多环境配置 |
| 05 接口文档 | `05-api` | `qa-api-doc` | 拉 Swagger 生成接口文档 |
| 06 执行 | `06-execution` | `qa-api-runner` / `qa-ui-automation` / 性能 / 安全 / 探索 / 兼容 / 移动端 | 真正跑测试 |
| 07 报告 | `07-report` | `qa-report` / `qa-bug-report` / `qa-release-check` | 出报告、提缺陷、上线门禁 |
| 08 归档 | `08-archive` | `qa-archive` | 一键打包全部产物 |

第 6 篇、第 7 篇、第 8 篇会分别深入 05–06、06 展开、07–08。

## 1.4 横切关注点（贯穿全程的 11 道质量门）

有 11 个技能**不属于任何单一阶段**，而是像「质检员」一样贯穿全流程，用来卡质量红线：

| 技能 | 角色 | 典型阻断场景 |
|---|---|---|
| `qa-risk-based` | 基于风险的测试（RBT），量化风险反推测试密度 | — |
| `qa-test-strategy` | 测试策略 / 计划制定 | — |
| `qa-ci` | 生成 CI/CD 流水线配置（GitHub Actions / GitLab / Jenkins） | — |
| `qa-mutation` | 变异分数（测试杀伤力）门禁 | 变异分数低于阈值 → 阻断 |
| `qa-flaky-detect` | 不稳定测试（flaky）检测 | flaky 率超阈值 → 阻断 |
| `qa-a11y` | 无障碍（WCAG 2.1 A 级）静态检查 | 存在 A 级违规 → 阻断 |
| `qa-visual-regression` | 视觉回归（DOM/属性快照）门禁 | 布局级回归 → 阻断 |
| `qa-unit-tdd` | 单元/TDD 方法学健康度 | 金字塔倒挂 / 覆盖率不达标 → 阻断 |
| `qa-chaos` | 混沌工程治理门（实验须受治理） | 关键实验无稳态假设 → 阻断 |
| `qa-code-review` | 代码评审启发式门（硬编码密钥等） | 硬编码密钥 → 阻断 |
| `qa-synthetic-monitoring` | 合成监控治理门（关键旅程须有断言+告警） | 无断言/无告警 → 阻断 |

> 这些「门禁」很多是**治理型**的：它们校验「规格是否完整/合规」，**不实际注入故障、不扫描生产、不做像素级对比**（真实能力须接专业工具）。这是诚实边界，第 9 篇会详细讲。

## 1.5 编排器 vs 单技能：你需要全装吗？

**不需要。** 这是最重要的认知：

- **单个技能 = 一份 `SKILL.md` + 几个 Python 脚本**。你直接说需求，平台加载后执行，互不依赖。
- **`qa-orchestrator`（编排器）= 可选的总控**。它负责「给每轮变更建目录、推断下一步该调谁、一键推进到归档」。不装它，你也能逐技能调用；装了它，一轮测试更规范可追溯。

套件提供三档「采用套餐」，按需取用：

| 套餐 | 你得到什么 | 适合谁 |
|---|---|---|
| **Starter** | 复制你需要的单个/几个技能目录，直接调用 | 只想解决单点测试任务 |
| **Gates** | 在 Starter 基础上接入 `signals/` 契约 + `qa-release-check`，把质量门禁挂进 CI | 想给流水线加发布卡点 |
| **Full** | 再引入 `qa-orchestrator`，按 8 阶段生命周期路由整轮变更 | 想标准化「从需求到归档」全过程 |

## 1.6 依赖与诚实边界（先有心理预期）

- **治理/编排层与 Agent 测试层共 36 个技能零第三方依赖**（纯 Python 标准库即可），仅 **4 个执行层技能**需要运行时依赖。
- **执行层 4 个技能需要运行时依赖**：`qa-api-runner`(requests/mysql/allure)、`qa-report` & `qa-test-case-gen`(openpyxl)、`qa-ui-automation`(playwright)。落地环境要确保这些包真实可用。
- **质量背书（当前版本）**：自测 **120/120** 全绿、零漂移，已通过甲方四位专家验收（综合 **9.53/10**）；所有「已通过」均对应可复跑证据，无假绿。
- **诚实边界**：脚本是确定性逻辑，不涉及模型推理；AI 能力来自宿主平台加载 `SKILL.md` 后的规划执行。部分门禁只校验规格、不实际执行外部动作，切勿误以为「装了就等于做了真实渗透/真实注入」。

> 为什么强调诚实？因为测试工具最怕「假绿」——看起来过了其实没测到。本套件的设计哲学是 **fail-closed（默认失败即阻断）** 和**明确声明能做什么、不能做什么**。
