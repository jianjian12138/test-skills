# 第 6 篇：接口测试全流程（第 5–6 阶段核心）

> 本篇目标：接口测试是大多数团队最高频的需求。学会用 `qa-api-doc` 拿接口文档、`qa-api-runner` 跑接口自动化（含多接口串联、数据库双校验）、`qa-api-contract` 做契约测试。这是第 5–6 阶段的核心。
>
> ⚠️ **依赖提醒**：`qa-api-runner` 属于**执行层**，需要运行时依赖 `requests`、`mysql-connector`、可选 `allure`。落地前先 `pip install requests mysql-connector-python allure-pytest`。

---

## 6.1 整体流程

```
有 Swagger/OpenAPI ？
   ├─ 是 → qa-api-doc 拉取 → api-doc.md / api-doc.json
   └─ 否 → qa-api-doc 指导从源码扫描提取接口清单
            ↓
   qa-api-runner 写场景文件 → 跑单接口 / 多接口串联 / DB 双校验 → Allure 报告
            ↓
   （可选）qa-api-contract 对比新旧 OpenAPI → 拦截破坏性变更，卡 CI
```

---

## 6.2 第 5 阶段：`qa-api-doc`（拿接口文档）

### 场景 A：已有 Swagger / OpenAPI

直接拉取，落盘为标准化文档：

```bash
python .workbuddy/skills/qa-api-doc/scripts/swagger_fetch.py \
    --url https://api.example.com/openapi.json \
    --output 05-api/api-doc.md \
    --save-json 05-api/api-doc.json
```

产出：
- `api-doc.md`：人读版接口清单（路径、方法、参数、响应）
- `api-doc.json`：机器可读版，供下游 `qa-api-runner` 消费

### 场景 B：没有文档服务器

如果只有代码（Java/Go/Python/Node），`qa-api-doc` 会**指导你从源码扫描提取接口清单**，先有文档再测，避免「每次变更就过期」的手工复制。

> 一句话：没有文档也能测，但先让 `qa-api-doc` 帮你把接口「显影」出来。

---

## 6.3 第 6 阶段：`qa-api-runner`（跑接口自动化）

### 它做什么

以**配置驱动的场景文件**运行接口测试，支持：
- **单接口测试**：一个请求 + 断言
- **多接口业务串联**：用 `extract` 提取上一步返回值，用 `${var}` 注入下一步（如先登录拿 token，再带着 token 下单）
- **数据库双校验**：接口返回正确还不够，还能查 MySQL 核对落库数据
- **Allure 报告**：产出可视化测试报告

### 怎么用（对话式）

> 「基于 `05-api/api-doc.json`，写登录接口的测试场景，验证返回 200 且 token 非空，跑一遍，出 Allure 报告。」

AI 会生成场景文件（JSON/YAML），再调用：

```bash
python .workbuddy/skills/qa-api-runner/scripts/run.py \
    --scenario 06-execution/scenario.json \
    --outdir 06-execution
```

### 多接口串联示意（伪代码）

```json
{
  "steps": [
    { "name": "登录", "req": {"post": "/login", "json": {"u":"a","p":"b"}},
      "extract": { "token": "$.data.token" } },
    { "name": "下单", "req": {"post": "/order", "headers": {"Authorization": "Bearer ${token}"}},
      "assert": { "status": 200 } },
    { "name": "核对落库", "db": "select status from orders where id=${orderId}",
      "assert": { "status": "PAID" } }
  ]
}
```

> 这正是 `qa-api-runner` 的强项：把「登录→下单→查库」这种业务流一键串起来。

## 6.4 第 6 阶段：`qa-api-contract`（契约测试，卡 CI）

### 它解决什么

后端改了接口，前端/调用方还按老的来 → 线上故障。`qa-api-contract` 对比**新旧两份 OpenAPI 规范**，自动识别**破坏性变更（Breaking Change）**并卡 CI。

- 内置 **35 条规则**（27 条 BREAKING / 8 条 WARN）
- 覆盖端点、参数、请求体、响应、组合类型、安全方案、服务器、弃用 8 个维度

### 怎么用

```bash
python .workbuddy/skills/qa-api-contract/scripts/contract_diff.py \
    --old old-openapi.json --new new-openapi.json \
    --signals-dir signals --fail-on
```

存在破坏性变更时写 `signals/qa-api-contract.json` 且 `blocking=true` → exit 1，CI 直接红。

> 适合接入发布流水线：每次后端提 MR，自动比对新旧契约，破坏兼容就拦下。

---

## 6.5 接口测试常见坑

| 坑 | 对策 |
|---|---|
| 没有接口文档，手工抄 | 用 `qa-api-doc` 拉取或扫源码生成 |
| token 要手动复制 | 用 `extract` + `${var}` 自动串联 |
| 只看接口返回，不问数据库 | 加 DB 双校验步骤 |
| 后端偷偷改字段导致前端崩 | 用 `qa-api-contract` 卡 CI |
| 缺 `requests` 等包跑不起来 | 先 `pip install requests mysql-connector-python` |
