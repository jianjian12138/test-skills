# 第 9 篇：横切质量门禁与 CI 集成（贯穿全程）

> 本篇目标：理解那 11 个「不属于单一阶段、像质检员一样贯穿全流程」的横切质量门禁，搞懂它们用什么机制卡质量红线（`signals` 契约 + fail-closed），并学会用 `qa-ci` 把门禁挂进 CI 流水线。

---

## 9.1 什么是「横切」？

前面 8 个阶段是**主线**（需求→归档）。而有些质量关注点**每个阶段都该有人盯着**——比如「有没有硬编码密钥」「测试是不是太 flaky」「无障碍达不达标」。这些就是**横切关注点**，由 11 个门禁技能承担。

> 类比：主线是流水线，横切门禁是流水线旁随时抽捡的质检员。

---

## 9.2 核心机制：`signals` 契约 + fail-closed

这是整套门禁的「神经中枢」：

1. 每个门禁技能运行后，往 `signals/<skill>.json` 写一个**信号文件**，里面有关键字段 `blocking`（是否阻断）和 `severity`（严重级）。
2. `qa-release-check` 启动时**扫描整个 `signals/` 目录**，**任一 `blocking=true` 即 exit 1**，发布被卡。
3. 设计哲学是 **fail-closed（默认失败即阻断）**：宁可误拦，不可漏放。

> 好处：**新增质量维度零改门禁**。你只要让新技能按 schema 写 `signals/<skill>.json`，发布卡点自动生效。

---

## 9.3 11 道横切门禁逐个看

| 技能 | 检查什么 | 典型阻断条件 |
|---|---|---|
| `qa-risk-based` | 基于风险的测试（RBT），Impact×Probability 定级，反推测试密度 | —（量化用，一般不阻断） |
| `qa-test-strategy` | 测试策略/计划制定 | — |
| `qa-ci` | 生成 CI/CD 流水线配置 | —（它本身是生成器） |
| `qa-mutation` | 变异分数（测试杀伤力） | 分数低于阈值 → 阻断 |
| `qa-flaky-detect` | 不稳定测试（flaky）检测 | flaky 率超阈值 → 阻断 |
| `qa-a11y` | 无障碍（WCAG 2.1 A 级）静态检查 | 存在 A 级违规 → 阻断 |
| `qa-visual-regression` | 视觉回归（DOM/属性快照） | 布局级回归 → 阻断 |
| `qa-unit-tdd` | 单元/TDD 方法学健康度 | 金字塔倒挂/覆盖率不达标 → 阻断 |
| `qa-chaos` | 混沌工程治理门（实验须受治理） | 关键实验无稳态假设/回退 → 阻断 |
| `qa-code-review` | 代码评审启发式门（硬编码密钥等） | 硬编码密钥 → 阻断 |
| `qa-synthetic-monitoring` | 合成监控治理门（关键旅程须有断言+告警） | 无断言/无告警 → 阻断 |

---

## 9.4 ⚠️ 诚实边界：哪些是「规格治理门」？

这点**必须讲清**，否则容易误用：

- `qa-chaos` / `qa-synthetic-monitoring` / `qa-code-review` 是**规格治理门禁**：它们**只校验规格/配置是否完整合规**——
  - `qa-chaos` 不实际注入故障；
  - `qa-synthetic-monitoring` 不实际探测生产；
  - `qa-code-review` 不解析 AST 做深度静态分析（只做确定性模式扫描）。
- `qa-a11y` 仅 WCAG 2.1 **A 级静态检查**（替代文本、表单标签、语言、标题层级等），**不做对比度/键盘可达性实测**。
- `qa-visual-regression` 对比 **DOM + 关键视觉属性**，**不做像素级图像 diff**。

> 真实能力（注入故障、扫生产、像素对比、AST 深度分析）须接专业工具（如 Chaos Mesh、Percy/Chromatic、Semgrep 深度规则）。本套件的定位是**「治理层把关」+「指引接专业工具」**，不是替代它们。

---

## 9.5 验证门禁真的在拦（示例）

以 `qa-a11y` 为例，写信号并卡发布：

```bash
python .workbuddy/skills/qa-a11y/scripts/a11y_check.py \
    --in web/ --signals-dir signals --fail-on
# 有 A 级违规 → 写 signals/qa-a11y.json (blocking=true) + exit 1
```

随后发布检查会自动拦下：

```bash
python .workbuddy/skills/qa-release-check/scripts/gen_release_checklist.py \
    --release release.json --signals-dir signals --out release-checklist.md --fail-on
# 读到 qa-a11y blocking=true → exit 1，CI 红，发布被卡
```

## 9.6 用 `qa-ci` 把门禁挂进流水线

`qa-ci` 从一份配置 JSON 生成**可直接提交的** CI 配置，默认串起质量门禁：

```
lint → 单元测试 → 接口/UI → 安全扫描
```

支持三种目标：

| 目标 | 配置 |
|---|---|
| GitHub Actions | `.github/workflows/qa.yml` |
| GitLab CI | `.gitlab-ci.yml` |
| Jenkins | `Jenkinsfile` |

> 推荐做法：把 `qa-release-check --fail-on`（聚合 signals）作为流水线的**最后一道发布门禁**，前面各阶段门禁写信号，最后统一裁决。这就是 fail-closed 在 CI 上的落地。

---

## 9.7 关于「验证状态」（tier 与 verified_by）

REGISTRY 里每个技能有 `tier` 和 `verified_by` 字段，诚实标注成熟度：
- **tier 1**：有脚本、已 smoke + CI 自测验证（绝大多数执行/门禁技能）
- **tier 2 / 3**：方法学/知识库类（如 `qa-chaos`、`qa-code-review`、`qa-synthetic-monitoring`、`qa-test-analysis`、`qa-ui-kb`），部分 `verified_by=pending`——即**方法已定义但暂未跑冒烟**，使用前留意该标注。

> 这不丢人，反而可信：能做什么、验证到哪一步，都写清楚，避免「看起来很全其实没测过」的假象。

---

## 9.8 小结

- 横切门禁 = 11 个贯穿全流程的质检员；
- 它们通过 `signals/<skill>.json` 的 `blocking` 字段通信；
- `qa-release-check` 聚合 signals，fail-closed 卡发布；
- 治理型门禁只校验规格，真实执行靠专业工具；
- `qa-ci` 把这一切接进 GitHub Actions / GitLab / Jenkins。
