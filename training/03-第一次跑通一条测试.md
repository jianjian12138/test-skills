# 第 3 篇：第一次跑通一条测试（最小闭环示范）

> 本篇目标：用 `qa-orchestrator` 编排器，5 分钟跑通「需求 → 用例 → 报告」的最小闭环。让你建立「产物落盘、阶段推进」的实感。
>
> 即使你不想用编排器，看完本篇也能明白：单个技能是怎么被调用的（最后有一节专门讲）。

---

## 3.1 编排器到底是什么？

回看 [第 1 篇](01-认识测试技能套件.md)：`qa-orchestrator` 是**可选的总控**。它做三件事：

1. **建目录**：给每轮待测「变更」建立一个标准化的 8 阶段工作区。
2. **指路**：扫描哪个阶段还没做，告诉你「下一步该用 `qa-xxx`」。
3. **推进**：按生命周期顺序把各阶段串起来，更新看板。

> 重要定位（务必记住）：编排器是**半自动**的。它规划、路由、跟踪，**不臆造执行结果**。真正跑接口/UI/性能测试，仍需要被测环境就绪、由你或 agent 实际触发。关键发布、归档节点的人工确认不能跳过。

---

## 3.2 场景设定（跟着做）

假设你要测试一个功能：**「用户登录」**。我们就用这个需求跑一遍。

---

## 3.3 步骤 1：建立变更工作区

在装好技能的**项目根目录**下，调用编排器的建目录脚本：

```bash
python .workbuddy/skills/qa-orchestrator/scripts/init_change.py \
    --base . \
    --change "用户登录功能测试" \
    --author "张三"
```

运行后，会在 `changes/` 下创建一个带时间戳缩写的目录，例如：

```
changes/
└── user-login-test/          ← 变更工作区（change_slug）
    ├── 01-requirement/       ← 需求阶段
    ├── 02-analysis/          ← 分析阶段
    ├── 03-cases/             ← 用例阶段
    ├── 04-testdata/          ← 数据/环境
    ├── 05-api/               ← 接口文档
    ├── 06-execution/         ← 执行
    ├── 07-report/            ← 报告/缺陷/发布
    ├── 08-archive/           ← 归档
    ├── README.md             ← 看板（进度总览）
    └── ROUTING.md            ← 路由说明
```

> 每个阶段目录现在都是空的，等待你往里填产物。

---

## 3.4 步骤 2：让编排器告诉你「下一步做什么」

```bash
python .workbuddy/skills/qa-orchestrator/scripts/route_next.py \
    --change changes/user-login-test --auto
```

输出类似：

```
下一步推荐技能：qa-req-spec
依据：01-requirement 阶段产物缺失
```

编排器扫描了 8 个阶段目录，发现 `01-requirement/` 还是空的，于是推荐你先做需求结构化。

---

## 3.5 步骤 3：按推荐调用子技能，落盘产物

现在你直接对 AI 说（或用对应技能）：

> 「把『用户登录』这个需求整理成规范需求文档，写入 `changes/user-login-test/01-requirement/requirement.md`。」

AI 会加载 `qa-req-spec`，产出一份结构化需求文档，包含：
- 功能模块划分
- 输入/输出规则
- 权限与异常边界
- 待确认问题

**这就是「阶段推进」的本质**：每个阶段调一个技能，把产物写进对应目录。

接着继续问编排器下一步，再调对应技能：

| 轮次 | route_next 推荐 | 你调的技能 | 产物落盘到 |
|---|---|---|---|
| 1 | `qa-req-spec` | 需求结构化 | `01-requirement/requirement.md` |
| 2 | `qa-test-analysis` | 拆解测试点 | `02-analysis/testpoints.md` |
| 3 | `qa-test-case-gen` | 生成用例 | `03-cases/cases.xlsx` |
| 4 | `qa-report` | 出报告 | `07-report/test-report.md` |

> 你**不需要背命令**。route_next 告诉你下一步用谁，你照着对 AI 下指令即可。

---

## 3.6 步骤 4：一键推进到归档（close_loop）

当主要阶段都做了，可以跑推进脚本，让编排器按序整理、更新看板：

```bash
python .workbuddy/skills/qa-orchestrator/scripts/close_loop.py \
    --change changes/user-login-test
```

它会列出待办阶段与对应技能，更新 `README.md` 看板，逐步推进。`--apply` 时会把已存在产物的阶段标记为「已完成」。

到这里的**最小闭环**就跑通了：需求 → 分析 → 用例 → 报告，全部产物归集在一个可追溯目录里。

---

## 3.7 进阶：断点续推与 checkpoint

实际工作中常会中断。编排器提供轻量审计：

```bash
# 标记某阶段完成（写一条 checkpoint）
python .../checkpoint.py --change changes/user-login-test --stage 02-analysis --status done

# 只看下一步该做什么（不自动执行，需人确认）
python .../checkpoint.py --change changes/user-login-test --resume

# 标记某阶段待重做
python .../checkpoint.py --change changes/user-login-test --stage 03-cases --retry
```

> 设计原则（DoD）：`close_loop` 推进每一阶段须满足「执行者无需再问即可继续」——产物已落盘、看板已更新、下一步明确。未达标不标 done。

---

## 3.8 不用编排器，怎么直接调单个技能？

很多小白其实**不需要编排器**。直接对话调用就行：

> 「帮我拉取 https://api.example.com/openapi.json 的接口文档」→ AI 加载 `qa-api-doc`
> 「把这份测试点生成 Excel 用例」→ AI 加载 `qa-test-case-gen`
> 「检查这次发布能否上线」→ AI 加载 `qa-release-check`

或者你想**手动跑脚本**（适合想看具体参数的人）：

```bash
# 接口文档：拉 Swagger → 落盘
python .workbuddy/skills/qa-api-doc/scripts/swagger_fetch.py \
    --url https://api.example.com/openapi.json \
    --output 05-api/api-doc.md --save-json 05-api/api-doc.json

# 无障碍门禁：有 A 级违规则 exit 1
python .workbuddy/skills/qa-a11y/scripts/a11y_check.py \
    --in web/ --signals-dir signals --fail-on
```

> 各技能目录下的 `scripts/` 里都有可直接运行的 Python 脚本；具体参数看每个技能的 `SKILL.md` 或 `references/`。

## 3.9 最小闭环速查表

| 想做 | 命令/动作 |
|---|---|
| 建工作区 | `init_change.py --base . --change "xxx"` |
| 看下一步 | `route_next.py --change changes/xxx --auto` |
| 推进归档 | `close_loop.py --change changes/xxx` |
| 标完成 | `checkpoint.py --change ... --stage 01-requirement --status done` |
| 直接调技能 | 对话说需求，或 `python qa-xxx/scripts/yyy.py ...` |
