# 第 7 篇：执行阶段的多种测试类型（第 6 阶段展开）

> 本篇目标：第 6 阶段「执行」是技能最多的阶段。本篇把 UI、性能、安全、探索、兼容、移动端六大类测试类型逐个讲清：什么时候用、用什么技能、怎么跑。最后用 `qa-execution` 把它们编排成进度矩阵。

> ⚠️ **执行层依赖提醒**：`qa-ui-automation` 需要 `playwright`；性能/安全多数靠外部工具（Locust/JMeter/ZAP/Semgrep/Trivy）配合。脚本本身是确定性逻辑，真正驱动执行的是你环境里的这些工具。

---

## 7.1 UI 自动化（3 步走）

UI 自动化最怕「页面一改，脚本全崩」。本套件用三件套稳住：

| 顺序 | 技能 | 作用 |
|---|---|---|
| 1 | `qa-ui-kb` | 建**页面知识库**：三层（元素描述/操作模式/选择器规则）+ 四层代码架构，沉淀稳定选择器 |
| 2 | `qa-ui-testid` | 扫描 React/Vue/HTML 源码，找出缺 `data-testid` 的交互元素，批量补唯一标识 |
| 3 | `qa-ui-automation` | 基于页面描述 JSON 生成 Page Object 骨架 + 冒烟用例，用 Playwright + Allure 跑出报告 |

> 关键：`qa-ui-testid` 让选择器用稳定的 `data-testid` 而不是易碎的 XPath/CSS 层级，是 UI 脚本寿命的关键。

```bash
# 扫描前端补 data-testid（dry-run 预览，不写文件）
python .workbuddy/skills/qa-ui-testid/scripts/scan_testid.py --src src/ --dry-run
```

## 7.2 性能测试（设计 → 脚本 → 分析）

性能路线**二选一**（共用 `qa-perf-design` 场景 schema）：

```
qa-perf-design（设计场景）
   ├─→ qa-perf-locust（生成 Locust .py，代码化/CI 友好）
   └─→ qa-perf-jmeter（生成 .jmx，无代码/分布式，适合已有 JMeter 资产）
            ↓ 跑完
   qa-perf-analysis / qa-perf-jmeter 的 analyze（解析结果）
```

| 技能 | 作用 |
|---|---|
| `qa-perf-design` | 设计 load/stress/endurance(soak)/spike 四类场景，明确并发、TPS、ramp-up、think-time、SLA |
| `qa-perf-locust` | 场景 JSON → 可运行 Locust 脚本 |
| `qa-perf-jmeter` | 场景 JSON → 标准 `.jmx`，并解析 JMeter CSV |
| `qa-perf-analysis` | Locust CSV → 吞吐、P50/P95/P99 延迟、错误率、瓶颈归因、SLA 是否达标 |

> 选 Locust 还是 JMeter？无代码团队/已有 JMeter 资产选 JMeter；要塞进 CI、代码化选 Locust。

---

## 7.3 安全测试（扫描 → 报告）

| 技能 | 作用 |
|---|---|
| `qa-security-scan` | OWASP Top 10 人工核查清单 + DAST(ZAP)/SAST(Semgrep)/依赖 CVE(Trivy) 使用指引 + **自带本地密钥/PII 泄露扫描脚本** |
| `qa-security-report` | 把 ZAP/Semgrep/Trivy 的分散 findings 归一成带 CVSS 思路评级（Critical/High/Medium/Low/Info）的安全报告 + 整改建议 |

```bash
# 本地密钥/PII 泄露扫描（确定性，无需外部工具）
python .workbuddy/skills/qa-security-scan/scripts/scan_secrets.py --in src/ --signals-dir signals
```

> 诚实边界：`qa-security-scan` 自带的是**本地静态扫描**；真正的 ZAP/Semgrep/Trivy 动态/深度扫描需你环境里有这些工具，技能提供的是指引与结果归一化。

---

## 7.4 探索性测试（`qa-exploratory`）

当**需求模糊、时间紧、要补脚本化盲区**时用。它把功能/风险点转化为一组**结构化测试章程（charter）**，并给 HTSM 启发式、常用 Tour、缺陷苗头信号、note-taking 模板。

> 探索性测试不是「随便点点」，而是「带着章程和启发式去测、边测边记」。

---

## 7.5 兼容性测试（`qa-compat-matrix`）

根据 **OS × 浏览器 × 设备 × 分辨率 × 网络** 维度，生成带优先级（必测/建议/可选）与「是否需云真机/云浏览器」标注的覆盖矩阵（CSV + Markdown）。覆盖 BrowserStack/SauceLabs/阿里云真机/腾讯 WeTest 接入与国产浏览器内核注意点。

---

## 7.6 移动端测试（`qa-mobile-autotest`）

移动 App 自动化流水线：摸清现状 → 列清单 → 生成资产 → 自检 → 中文交付。含：
- **定位金字塔**：accessibility id 优先，XPath 兜底
- **五维质量 rubric**（可运行性/定位健壮性/可维护性/稳定性/覆盖透明度，<70 必须补全）
- **fault-diagnosis 决策树**：脚本失败快速定位根因

---

## 7.7 统一编排：`qa-execution`

当一轮要跑**多类测试**（UI/API/性能/安全），用 `qa-execution` 从用例+结果 JSON 生成**执行进度矩阵**（按模块/类型/状态交叉统计），并把每个失败项路由到对应下游技能处理。

---

## 7.8 一张表速查

| 测试类型 | 主技能 | 是否需要外部工具 | 典型产出 |
|---|---|---|---|
| UI 自动化 | `qa-ui-kb` → `qa-ui-testid` → `qa-ui-automation` | Playwright | Page Object + 冒烟报告 |
| 性能 | `qa-perf-design` + (Locust/JMeter) + `qa-perf-analysis` | Locust 或 JMeter | 场景 + 瓶颈报告 |
| 安全 | `qa-security-scan` → `qa-security-report` | ZAP/Semgrep/Trivy（自带本地扫描） | 安全报告 |
| 探索性 | `qa-exploratory` | 否 | 章程 + debrief |
| 兼容性 | `qa-compat-matrix` | 云真机/云浏览器（可选） | 矩阵 CSV/MD |
| 移动端 | `qa-mobile-autotest` | Appium（思路指引） | 资产 + rubric |
| 统一编排 | `qa-execution` | 否 | 进度矩阵 |

---

## 7.9 小结

第 6 阶段不是「一个技能」，而是一组**按需取用**的执行技能。记住：
- UI 走 `kb → testid → automation` 三步稳选择器；
- 性能先设计再选 Locust/JMeter；
- 安全先扫再出报告；
- 模糊/紧急用探索性；
- 多类并发跑用 `qa-execution` 编排。
